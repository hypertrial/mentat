# Cockpit review decisions v1

Add optional `reviewDecision.prepare`, `reviewDecision.commit`, and `reviewDecision.get` bridge capabilities. A local operator can reject or defer an exact validated run evaluation with a bounded reason, or explicitly resume that same deferred evaluation. A new run or candidate starts pending. Failed checks do not prevent reject or defer, but the current scope, candidate, evidence manifest, approval, and required-check policy must be validated. Commit rechecks the reviewed identity and uses an expiring instance-scoped token.

Persist immutable request IDs, actor assertion, action, reason, exact evaluation identity and timestamps in an atomic durable journal. Identical committed requests are recoverable by receipt; mismatched request-ID reuse fails. Corrupt or unreadable journal state fails closed. Reject closes that evaluation; only resume of its matching defer reopens it. Existing accepted history remains immutable. Both CLI and bridge acceptance share the gate and per-run cross-process serialization with decision commits. Keep legacy acceptance records and existing v1 wire shapes compatible.

Regression surfaces include stale candidate, evidence, approval or policy at commit; duplicate request and restart recovery; reject/defer/resume transitions; corrupt journal; concurrent decisions and acceptances; and agreement between CLI and bridge. Run focused bridge and CLI tests, `scripts/verify-fast`, `scripts/verify`, and the dedicated Linux `scripts/verify-worker` gate; record unavailable prerequisites and exact results in implementation evidence.

## Interface and storage

`prepare` takes `{repo, base, runner, state?, revision, runId, action, reason?, requestId, hostConsent?}`. Actions are `reject`, `defer`, and `resume`; reject/defer require a nonblank reason of at most 2,000 characters. Request IDs contain 1–128 ASCII letters, digits, `_`, or `-`. A new prepare returns an expiring token and the reviewed evaluation; an identical already committed request returns its receipt. `commit` takes `{token}` and returns `{receipt}`. `get` takes `{requestId, runId, state?}` and returns the exact matching `{receipt}` without requiring the historical evaluation to remain current.

The receipt contains `requestId`, `action`, `reason`, `actor`, `evaluation`, and `committedAt`; the evaluation includes the run and manifest identity, candidate, complete project scope, and approval. A single operator-owned journal is limited to 1,000,000 bytes on both read and write. It is atomically replaced and its directory synced, under one cross-process lock also held during CLI and bridge acceptance checks and writes. The journal never discards history; a full, malformed, or unreadable journal blocks new decisions and acceptance until repaired. Request IDs are unique across evaluations and actions. A validated existing acceptance receipt is preserved.
